## R11.4: CORS i kompresja na domenie własnej w Cloudflare R2

1. **CORS: ustawienie** (https://developers.cloudflare.com/r2/buckets/cors/, „Last updated Sep 23, 2026”). Politykę dodaje się w dashboardzie: R2 → bucket → Settings → CORS Policy → Add CORS policy (zakładka JSON). Można też użyć `npx wrangler r2 bucket cors set <BUCKET> --file cors.json`. `AllowedOrigins` musi być w formie `schemat://host[:port]`, bez ścieżki. Dozwolone jest `*`.

2. **CORS na domenie własnej.** Ta sama strona (stan na 23.09.2026): domena własna z polityką CORS zwraca nagłówki CORS automatycznie. Żądanie musi mieć nagłówek `Origin`. Po zmianie polityki trzeba wyczyścić cache dla nazwy hosta (Cache Purge). Propagacja zmian zajmuje w rzadkich przypadkach do 30 s.

3. **Kompresja, reguły** (https://developers.cloudflare.com/rules/compression-rules/, „Last updated Aug 14, 2026”). Cloudflare kompresuje część odpowiedzi domyślnie, zależnie od typu treści. Compression Rules pozwalają zmienić algorytmy dla typów lub rozszerzeń. Reguły działają tylko, gdy rekord DNS jest przez proxy Cloudflare. Czy `application/json` jest na domyślnej liście: NIEZWERYFIKOWANE, bo strona linkuje do opisu domyślnej kompresji, którego nie otworzyłem.

4. **Kompresja, ustawienia** (fragment strony https://developers.cloudflare.com/rules/compression-rules/settings/ z wyszukiwarki, bez daty). Opcja „Enable Brotli and Gzip compression” wybiera Brotli, a w razie braku wsparcia gzip. To ustawienie reguły, nie gwarancja dla odpowiedzi JSON z R2. Według fragmentu PR w repozytorium dokumentacji (bez daty, nieoficjalne) Brotli jest domyślnie włączony w planach Free i Pro, a wyłączony w Business i Enterprise. NIEZWERYFIKOWANE w oficjalnym źródle.

5. **SDK JavaScript v3** (https://developers.cloudflare.com/r2/examples/aws/aws-sdk-js-v3/, „Last updated Oct 26, 2026”). Pobrana wersja strony konfiguruje klienta tylko przez endpoint, `region: "auto"` i dane logowania. Nie ma w niej opcji `requestChecksumCalculation` ani `WHEN_REQUIRED`. Paczka cf-r2-sdk i inne strony cytują ten sam adres z `WHEN_REQUIRED`. NIEZWERYFIKOWANE w aktualnej wersji oficjalnej strony.

6. **`aws s3 sync` i sumy kontrolne.**
   - Strona AWS CLI dla R2 (https://developers.cloudflare.com/r2/examples/aws/aws-cli/, „Last updated Oct 15, 2026”) nie wspomina o sumach kontrolnych. Pokazuje `aws configure` z `region auto` i przykłady `s3api`/`presign`.
   - AWS (https://docs.aws.amazon.com/sdkref/latest/guide/feature-dataintegrity.html, data strony nie widoczna): nowe wersje AWS CLI same liczą sumę CRC przy wysyłaniu. Dla starszych wersji w pliku konfiguracji ustawia się `request_checksum_calculation` oraz `response_checksum_validation` na `when_required`, czyli suma jest liczona tylko wtedy, gdy operacja jej wymaga.
   - Zewnętrzny artykuł o R2 (https://roboin.io/article/2025/06/05/how-to-fix-cloudflare-r2-internal-error, po japońsku, 5.06.2025): AWS CLI od 2.23.0 i 1.37.0 wysyła nagłówki, których R2 nie przyjmuje. Obejścia: obniżyć wersję do 2.22.35 lub 1.36.40, albo podać `--checksum-algorithm CRC32`. Ten sam artykuł podaje analogiczne obejście dla JS SDK od wersji 3.729.0.
   - **Odpowiedź:** dokumentacja Cloudflare nie mówi, czy `aws s3 sync` wymaga obejścia. Zewnętrzne źródła wskazują, że przy nowszych wersjach CLI może być potrzebne `request_checksum_calculation = when_required`. Nie testowałem tego na koncie R2.
